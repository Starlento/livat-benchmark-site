STABLE RELEASE / v1.9.0

45 tasks. All scenes implemented.

27 parking handoff tasks and 18 exit tasks.
Default static, complex static and dynamic: 15 tasks each.

Six task categories

From a named building to any exit.

Named building 9, any mall lift lobby 9, special bay 6, store 3, named exit 9 and any exit 9. Each category carries equal weight. Parking tasks start at the Fuquan Rd (9), Jinzhong Rd (10) and Xiehe Rd (8) entrances. Paired scene variants share their start and user prompt.

Physical and visual scenes

Occupancy, queues and releases.

Physical scene vehicles constrain occupancy and navigation; contact with the ego vehicle ends the attempt as a failure. Visual-only vehicles affect the image without changing occupancy or reference cost. Finite queues, triggered bay releases and blocked exits follow each scene's declared behaviour.

Simulation-time scoring

Waiting is part of the task.

Efficiency uses elapsed simulation time and manoeuvres: C = 0.018 × sim_time_s + 0.40 × manoeuvres. Movement, explicit waits and simulation ticks used for image capture count. Model inference and network waits while the simulation is paused do not.

The server, exported client and Schema use the same package release. Scene implementation does not imply that every visual difficulty requirement has passed; see the validation scope and known limitations. Release notes ↗ · Specification ↗ (repository access required)

02 / GET STARTED

One wheel, two platforms.

Linux and Windows share one pure-Python package.
The CARLA SDK must match the server and the Python ABI.

01

Prepare the simulation environment

Install CARLA 0.9.16 ↗, then deploy the Livat B3 v1.3.0 map and the matching CARLA Python API. Download and installation instructions for the map package are to be provided.

02

Install the benchmark

Download the wheel from the v1.9.0 stable release ↗. The release is hosted in a private repository and requires the corresponding access. Installing this package does not install or replace the CARLA SDK.

03

Start the task service

Launch a dedicated CARLA instance following the map delivery instructions, then start the evaluator. Each task has exclusive use of a synchronous clock and gets its own HTTP address and token. Cameras use the map's default exposure.

The line continuations are for Bash. In PowerShell, join the command into a single line. Replace <case_id> with a task ID returned by list-cases.

The harness uses BenchClient from the same package in its own process; no second client package is needed. You can also run livat-bench export-client ./public-client to export a standard-library-only client, types, Schema, and examples of segmented image retrieval and disconnect recovery.

03 / HTTP INTERFACE

Let the system choose, through the interface.

The harness runs in its own process.
Every request carries the task's Bearer token.

RequestCapability
GET /metadataRead all six cameras, intrinsics and extrinsics, vehicle geometry and motion constraints
GET /stateQuery the current lifecycle, in-flight requests, sim_frame, action_seq and budget
GET /observationRead same-frame RGB references, local occupancy, bay geometry, geometric rules and certified paths; view=decision returns a lightweight observation for decision-making
GET /local-slotsRead anonymous bay geometry and occupancy evidence for the current or a past observation; read-only, does not advance the simulation
GET /snapshot?observation_id=…Download a fixed observation, its manifest and the matching same-frame PNGs in one call; omit the ID to get the latest
GET /images/…Read published raw RGB images; past images remain readable while the task's HTTP service is running
GET /requests/<request_id>Query an action receipt; resume the same request after a timeout or disconnect
GET /resultRead the fixed final public result; repeated reads do not re-score
POST /moveDrive a self-chosen arc length distance_m along the current path_id; returns an action receipt
POST /turnaroundUse an available dead-end turnaround capability from the current observation; the heading flips 180° at the same rear-axle position and counts as three turns
POST /waitWait in place for 1–10 integer simulation seconds; elapsed simulation time counts towards efficiency, and the receipt references the new endpoint observation
POST /camerasSelect a subset of cameras or turn all of them off; device descriptions are always complete
POST /costsReport cumulative model requests and token cost
POST /submitParking tasks submit the polygon_local_m returned by the current local_slots; exit tasks end automatically on reaching the zone
POST /abandonVoluntarily end the current task, recorded as a valid zero-score attempt; this is not an infrastructure error and earns no free retry
POST /acknowledgeExplicitly confirm after saving the final result, closing the HTTP service early

After observing, use the new path capabilities

Each new observation issues new path capabilities and per-observation bay IDs; past snapshots remain readable. Geometry submissions reference vehicle-frame coordinates from the current observation. A move must be at least 0.2 m and no longer than the current path's limit; forward or reverse is determined by the path direction.

To observe along the way, split the move

A move produces only an endpoint observation, with no images along the way. After each segment, call snapshot(receipt.output_observation_id) to get the observation and images, then decide using the new paths. When a move is cut short by the budget or an exit task completes automatically, check the actual distance and the result so that an old observation is not mistaken for the endpoint view.

Resume execution with the original request identity

move, turnaround, wait, cameras, costs, submit and abandon all carry a request_id. After a timeout, query it with receipt() or wait_for(). The same ID with the same content is never executed twice; reusing an ID with different content causes a conflict.

Local navigation with precise continuation

Entry points, curve-segment identities and arc-length stations help verify the remaining route after a segmented move. Frontier branch IDs are used for grouping; the next move still uses the latest path_id. termination_reasons explain the current certification limits and do not reveal hidden roads; road intervals do not indicate bay match scores or extra handover restrictions.

Six cameras, captured on demand

The Model 3 carries one camera at the centre of the windscreen at 2560 × 1440, FOV 90°; two on the B-pillars, two on the front fenders and one at the rear, each at 1920 × 1080, FOV 140°. 1 Hz is the sensor sampling clock, not a video stream during motion.

Two kinds of endpoint; confirm after saving the result

Parking tasks directly submit the four-corner geometry of a bay perceived in the current frame; there is no candidate-registration step or mandatory stationary wait, and only one final submission is allowed. Actual occupancy, true dimensions, goal match, unique geometric correspondence, observation freshness, the motion contract and the budget all still count towards the score. Exit tasks end on reaching the zone, with no bay selection or full stop required; read result() to save the final score. Receipts, results and past images are retained for at most 120 s; call acknowledge() after saving.

For all fields and constraints, see the public protocol ↗ and the client guide ↗ (repository access required). The business action counter action_seq is separate from the actual simulation frame sim_frame; a completed receipt does not mean the task succeeded.

04 / OBSERVER & REPLAY

Independent observation, faithful run records.

The observer channel is off by default, read-only and uses separate credentials.
It provides a unified map API that a WebUI can render.

Live observation

Add --observer-port 8766 when starting a single task or campaign-next to enable a separate process on a local port. It serves the scene, state, events, public navigation, actually captured snapshots and the final public result; it does not serve answers, per-bay scores or reference routes.

Static map without a simulator

livat-bench observer --api-port 8767 serves only the unified GET /scene and needs neither CARLA nor task records. Building polygons keep their parts and holes; charging / accessible / compact markers are independent and may overlap.

Offline replay

Use livat-bench replay <run_folder>/public --api-port 8766 to read saved records. Replay does not connect to CARLA and does not re-score; incomplete runs remain incomplete.

A harness project's WebUI may use the map for display to humans; models, policies and execution clients must not call or use it, and it must never flow back into inputs, memory, caches or tool results. The display channel has its own port and credentials. Semantic building boundaries are not physical walls, facilities / fixed occupancy do not determine task eligibility, and map entrances and exits are neither success zones nor proof of drivability. Records, images and tokens stay on the evaluator side. Observer and replay guide ↗ (repository access required)

EVALUATION / SCOPE

What is evaluated is the whole system.

The system is responsible for visual understanding, planning, memory and choice; the evaluator provides the environment, motion contract and scoring. This site publishes no model scores. Offline reference replays, private-route controller fixtures and formal model evaluations are recorded separately.

A valid parking handoff scores 100 × (0.50 Q + 0.50 E) and a valid exit task scores 100 × E. Q is destination match; E compares executed simulation time and manoeuvres with the appropriate reference, using C = 0.018 × sim_time_s + 0.40 × manoeuvres. The total averages the six category means with equal weight. Driving distance remains a diagnostic metric and a budget constraint.

Simulation time runs from the first recorded trajectory frame to the terminal frame, including movement, explicit waits, primitive binding, turnarounds and image-capture ticks. Paused model inference, network latency and reading an existing observation or image do not add simulation time. Initial sensor preparation precedes the scored trajectory.

Destination match still uses the straight-line distance from the bay centre to the nearest point of the building polygon: ≤20 / 40 / 60 / 80 m gives Q = 1 / 0.75 / 0.5 / 0.25, and beyond 80 m gives 0. Obstacles along the line do not affect this match distance; occupancy, dimensions and type are checked independently.

The 108 references comprise 90 parking quality tiers and 18 exit routes. Ordinary references use the existing forward-search definition; dynamic event witnesses retain their designed triggers, waits and returns, which can include reversing or a legal turnaround. Optimal scoring references and complete event witnesses are recorded separately. References are verified feasible cost bounds, not a proof of globally optimal behaviour across all policies.

v1.9.0 validation. All 45 tasks and 108 references passed offline checks for the release snapshot. A separate wheel installation passed integrity, offline-import, read-only-resource and client-export checks, reusing all 45 dependency-matched reference records. The 356-test result and 29 retained-trajectory comparisons are carried forward with explicit source-equivalence evidence and keep their original build identities. Packaging and this website update add no new CARLA run or RGB review.

Known limitations. Early elevator-lobby signage is visible in cases 011/012 and 014/015, so their strict semantic-concealment requirement remains unmet. Some historical evidence and external source files are missing or changed; the full source audit is not marked as passed. Existing image reviews cover only the frames actually viewed.

After upgrading, start a new campaign. Earlier scores, incomplete runs and recovery records retain their original builds; they are not merged into a new result. The four-task development sample and private-route fixtures are not autonomous model benchmark results.
